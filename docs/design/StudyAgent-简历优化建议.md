## 一、市场要求速览（2026-08 招聘 JD 分析结论）

按稀缺度排序：**评测**（89% 团队有 observability，只有 52% 有真实 eval，最稀缺）> RAG 全链路 > 工具治理 > multi-agent（须说清为何拆）> 生产可靠性（checkpoint/恢复/成本意识）。

面试形态：不考 LeetCode，考 **trace walkthrough**（"某次失败，哪个工具被调、返回了什么、你怎么发现的"）、**eval 设计**（"幻觉率 4% 你怎么办"——想听测量方案，不想听"换模型"）、**containment**（"agent 能做什么你无法撤销的事"）。

红线：❌ 不写"自研 Runtime"（招来与 LangGraph 的必输比较）❌ 不写 prompt engineering 当亮点 ❌ 无数字的 bullet ❌ 编造数字。

## 二、核心原则：每条 bullet 从产品问题出发

写法模板：**功能上遇到什么问题 → 技术方案 → 数字**。不是"我想展示什么技术"。

特别注意（本次讨论修正的两点）：

1. **不出现"状态机"**。旧简历"像 workflow"的病根就是后端状态机驱动流程。新设计是 agentic 的：模型在 loop 里自主决定下一步，进度是模型经工具读写的**数据**（todo/plan），后端不编排流程、只守**不变量**（配额、权限、"有未完成 todo 不许结束会话"）。后端校验要讲，但身份是**护栏**，不是引擎。
2. **工具治理必须写清与 AgentScope 的边界**。框架已提供：大结果 offload、allow/approve/deny 三态权限 + HITL、模型层重试。框架不提供（通用框架不懂业务语义）：业务配额、权限参数服务端注入、写入业务幂等。简历写"在通用治理之上补业务治理层"——知道框架边界本身就是考点。

## 三、简历 Bullet（方案 A 修正版，共 7 条）

### 项目描述

> 面向学习备考场景的 AI Agent：用户上传学习资料构建个人知识库，agent 自主规划学习路径，逐知识点完成讲解、答疑、测验与复习卡生成，卡片导出 Anki 形成学习-复习闭环。基于 AgentScope Java 构建，重点在检索质量的量化优化、生成内容的自动质检与运行时的可控可恢复。

### B1 · 学习主链路闭环（项目主心骨，放第一条）

**产品问题**：学习是跨多天的长任务，agent 要能自主推进、中断可续、内容不断层。

**写法**：
> 基于 AgentScope 构建学习编排 agent：根据用户目标与知识库生成学习计划（todo 工具维护，agent 自主推进），逐知识点完成讲解 / 答疑 / 测验 / 卡片生成，知识点完成后触发 context compaction 控制上下文规模；后端对会话终止、写入范围做不变量校验（有未完成计划不得结束会话）；基于 checkpoint 实现跨天学习会话恢复；复习卡经 AnkiConnect 单向导出 Anki，形成学习-复习闭环。

**数字**：▢ 长会话 compaction 后 token 成本降幅 ▢ 崩溃恢复成功率（kill -9 实测）
**追问预备**：为什么 compaction 在知识点边界触发而不是固定轮数？（知识点完成 = 语义边界，压缩损失最小）checkpoint 存什么、粒度为什么这么选？

### B2 · RAG 策略对比与量化优化（最能展开的一条）

**产品问题**：讲解和答疑的质量上限 = 检索质量；中文教材 + 术语混排，默认配置检索很差。

**写法**：
> 设计并量化对比 4 种检索策略（BM25-only / 向量-only / 混合 RRF / 混合 RRF + 父子二跳）：结构感知分块（标题/段落/代码，超长 fallback 到 token window）+ 父子分块（子块精准召回、父块回填上下文，解耦精准性与完整性）；针对中文对比 standard / IK / SmartCN 分词器的 BM25 召回差异；引入按检索器分离的相关性阈值过滤误召回。在 ▢ 条评测集上 Recall@K 对比择优，索引采用版本化物理索引 + 读写别名，策略变更时 bulk 重建、评测通过后原子切换、保留旧索引可回滚。

**数字**：▢ 各策略 Recall@3/@6 ▢ 分词器对比差异 ▢ 阈值的 precision-recall 取舍点 ▢ P50/P95 延迟
**追问预备**：RRF 的 k 怎么定？多个子块命中同一父块怎么聚合？为什么不上 rerank（候选量小收益待验证，列为后续实验）？

### B3 · 测验/卡片的 LLM 质检 + 改动回归（judge 的产品化表述）

**产品问题**：模型出的题不能直接给用户——选项可能无唯一正确答案、题目可能是编的不在知识库里。人工审每道题不现实。

**写法**：
> 构建生成内容自动质检：测验与卡片生成后先过 LLM-as-judge（依据性——题目是否可由源文档回答、选项唯一正确性、解析正确性），不合格打回重出；judge 先在 ▢ 条自标注样本上校准至与人工判断一致率 ▢%；同一评测集同时作为回归门禁——分块参数或 prompt 变更后重跑，分数下降即阻止合入。

**数字**：▢ 质检拦截率（生成 N 道题拦下多少不合格）▢ judge 与人工一致率 ▢ 单次回归成本（元）
**追问预备**：judge 自己幻觉怎么办（校准 + 低温 + 结构化输出 + 只判可验证维度）？为什么用便宜模型做 judge？位置偏好/长答案偏好怎么缓解？

### B4 · 异步出题委派（subagent 的产品化表述）

**产品问题**：出一套题要检索原文 + 逐题出题 + 配解析，约 30-45s；串行则用户干等，且出题用的大量检索原文会灌进主对话 context，把学习历史挤出去。

**写法**：
> 将测验/卡片生成委派给独立 subagent 异步执行：主 agent 提交 job 后继续与用户对话，经进度查询工具获知完成；subagent 独立 context（用完即弃）实现上下文隔离，返回结构化结果由业务层校验后落库（subagent 不直接写业务状态）。

**数字**：▢ 主对话阻塞时间对比（串行 vs 委派）▢ 主 agent context 规模对比
**追问预备**：subagent 失败怎么办（job 状态可见，主 agent 可告知用户并重试）？为什么不让 subagent 直接写库（权限收敛 + 结果校验单点）？

### B5 · 业务级工具治理（收窄后的诚实版本）

**产品问题**：真实缺陷——旧实现里"生成 1-5 张卡"只写在 prompt 里，模型交 200 张就写 200 行，用户卡库被垃圾卡塞满。prompt 约束不是约束。

**写法**：
> 在 AgentScope 通用治理（大结果 offload、HITL 审批、模型层重试）之上补业务治理层：写入配额服务端强制（超限截断 + 告警而非信任 prompt）、userId / 知识库范围等权限参数一律服务端注入（模型不可见不可改）、写入业务幂等（同一知识点重复生成不重复入库）。

**数字**：▢ 配额拦截的实测案例 ▢ 检索结果经体积治理后单次调用 token 降幅
**追问预备**：AgentScope 治理边界在哪、为什么这几件必须自己做（通用框架不懂业务语义）？prompt 注入让模型改 userId 会发生什么（参数根本不在模型可写的 schema 里）？

### B6 · 摄入管道与索引运维（偏后端强化条，合并旧简历遗产）

**产品问题**：上传后解析/向量化是长链路，失败要可见可补；分块参数或 embedding 模型一变，全量索引语义作废，要零停机重建。

**写法**：
> 构建文档摄入管道：RocketMQ 解耦上传与向量化（2MB 文档响应 10s→120ms），管道各阶段失败状态可见、MQ 消费幂等、Canal 补偿 MySQL→ES 最终一致；分片并发上传 + Redis Bitmap 断点续传（400MB 上传 20s→9s）；音视频经云端 ASR 转写并按时间戳对齐，检索命中可定位到视频具体时间点。

**数字**：10s→120ms、20s→9s 为旧版已实测数字可沿用；▢ ASR 链路吞吐（新增待测）
**追问预备**：为什么用 Canal 补偿而不是双写（双写无法保证一致性，binlog 是唯一可靠事实源）？

### B7 · 轻量知识图谱 + 前置回溯

**产品问题**：用户学到"泛型"卡住，往往是前置概念（类与对象、类型系统）没掌握——需要知道"学这个之前该会什么"。

**写法**：
> 从学习材料中经 LLM 抽取概念实体与前置依赖关系构建轻量知识图谱（MySQL 存储 + BFS 遍历，刻意不引入图数据库），学习新知识点时回溯前置概念、结合用户已学记录生成补课建议。

**数字**：▢ 每份资料抽取实体数 ▢ 前置关系正确率（评测方法见 §四）
**追问预备**：为什么不用图数据库（几百节点 BFS 毫秒级，Neo4j 是为万级+多跳设计的，引入即过度工程）？LLM 抽取的关系怎么验证？

## 四、无真实用户的量化方案（关键设计）

你的约束：找不到学生实测。业界对此有成熟做法，核心是**合成 + 自标注 + 模拟用户**，简历上写"在 N 条评测集上"即可，个人项目没人期待 user study。

### 4.1 检索评测（B2 的数字来源）

- **合成查询**：从已索引的 chunk 反向生成问题（LLM 出题，ground truth = 源 chunk id），天然自带标注。生成 100-200 条，人工抽检 20% 剔除坏例。
- **自标注补充**：你本人就是目标用户（学习者），手工写 30-50 条真实感查询并标注相关 chunk——你标得比任何众包都准。
- 两者混合构成黄金集，Recall@K 直接可算。

### 4.2 生成质量评测（B3 的数字来源）

- **judge 校准**：自标注 20-30 条测验题的合格/不合格（这个判断你完全有能力做——题目对不对你看得出来），迭代 judge prompt 直到一致率达标，然后 judge 才有资格批量打分。
- **自一致性检查**（不需要任何标注的巧妙角度）：让模型**只看源 chunk 回答自己出的题**——答不对说明题目超纲或有歧义，自动判不合格。零人工成本的质检维度。

### 4.3 学习流程/轨迹评测（B1、B4 的数字来源）

- **模拟学生**：用一个 LLM 扮演学生（persona：会追问、会答错题、会跑题），驱动完整多轮学习会话——这是 τ-bench 等业界基准的标准做法。可测：会话完成率、终止正确性（该结束时结束了吗）、工具调用正确率、原地打转率。
- 模拟学生的另一个用途：批量生成长会话，用于测 compaction 的 token 节省和恢复成功率。

### 4.4 纯系统指标（不需要任何用户）

延迟 P50/P95、token 成本、context 规模、崩溃恢复成功率（脚本 kill -9 反复实测）、配额拦截行为——全部单机可测。

### 4.5 知识图谱评测（B7 的数字来源）

- **章节序一致性检查**（自动，零标注）：教材本身有章节顺序，前置关系边理应大多指向更早章节——统计"前置边与章节序一致"的比例，作为自动指标。
- **自抽检**：抽 50 条关系人工判断（你是学习者，判断"A 是否是 B 的前置"有资格）。

### 诚实边界

简历与面试口径统一为："在 N 条（合成 + 人工标注）评测集上"。被问"有没有真实用户数据"就答实话：个人项目，用合成查询 + 模拟用户 + 自标注黄金集做离线评测，这套方法本身就是业界做 agent eval 的标准手段——**评测方法论恰恰是展示点，不是遮掩点**。
