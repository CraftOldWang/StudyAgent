# StudyAgent 选型对比手册

**日期** 2026-09-02 · **用途** 实现参照 + 面试准备

每个选择点给出候选方案、对比、当前结论。标记说明：
- 【已定 D-xxx】已有决策，实现者照做；面试时按"为什么选它"准备
- 【待定】执行时需实验或由用户拍板；面试时按"我如何做这个决策"准备

面试的真正考点不是"你做了什么"，而是"**为什么不用另一种**"。每节末尾附追问预备。

---

## 1. Agent Runtime 基座 【已定 D-009：AgentScope Java 2.0】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 完全自建（接管 Loop/Context/Memory/Checkpoint/Trace） | 控制权最大，每一层都能讲 | 2-3 周起步；"自研框架"招来与 LangGraph 的必输比较；时间预算被 runtime 吃掉，垂类与评测反而没空做 |
| B. Spring AI 默认循环 | 改动最小 | 工具轮次框架内部执行，应用层不可见：配额、checkpoint、trace 全做不了 |
| C. Spring AI 作低层 adapter + 自建 Loop | provider 协议不用自己写，控制权在手 | 仍需自建 Context/Memory/Checkpoint/Trace 整套 |
| D. LangChain4j | 生态较大 | Java 侧 agent 能力（分层记忆、session 恢复、子 agent）弱于 AgentScope Java 2.0 |
| E. **AgentScope Java 2.0** ✅ | Loop/Context/双层记忆/Checkpoint/Trace/子 agent 开箱即用；时间预算全留给垂类+RAG+评测 | 依赖框架演进；业务治理需自己补层 |

**为什么选 E**：项目的差异化在"垂类 + 检索质量 + 可评测"，不在 runtime 本身。框架已生产就绪的能力重写一遍是低杠杆投入。
**追问预备**：AgentScope 和 LangGraph 什么关系（前者 Java 原生、含 harness 级能力；后者 Python 生态）？框架哪些地方不够用（→ §2 治理边界）？如果框架停止维护怎么办（核心是理解它做了什么，机制可迁移）。

## 2. 工具治理边界 【已定：框架通用层 + 自建业务层】

| 层 | 谁提供 | 内容 |
|---|---|---|
| 通用治理 | AgentScope | 大结果 offload（超限落盘留占位符）、allow/approve/deny 三态权限 + HITL、模型调用重试 |
| 业务治理 | **自建** | 写入配额（一次最多 N 张卡，服务端截断+告警）、权限参数服务端注入（userId/KB 范围不在模型可写 schema 里）、写入业务幂等（同知识点重复生成不重复入库） |

**为什么这条线画在这**：通用框架不懂业务语义——它不知道"5 张卡"是配额、不知道哪个参数是权限参数。
**追问预备**：prompt 注入让模型改 userId 会怎样（参数根本不在 tool schema 里，模型无从写起）？为什么不信 prompt 里的"1-5 张"（旧实现真实缺陷：模型交 200 张就写 200 行）？

## 3. 多 Agent 协作 【已定 D-012：异步 job + 进度查询工具】

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| A. 同步进程内委派 | 实现最简、低延迟、好调试 | 出题 30-45s 用户干等；父进程崩溃连带 | 短任务 |
| B. **异步 job + 进度查询** ✅ | 主对话不阻塞；context 隔离 | 需 job 状态管理 | 出题/制卡这类分钟级任务 |
| C. 消息驱动 Worker（MQ） | 故障隔离、水平扩展、背压 | lease/幂等/取消/结果回注全要设计，单机单用户纯属过度工程 | 多实例生产系统 |
| D. 多角色协商（Coach/Critic 投票） | 论文好看 | 成本×N、延迟×N、不服务任何功能点 | 不适用本项目 |

**演进话术**：首版 B；如果将来要多实例部署，升级路径是 C，接口（task contract / lineage / budget）从一开始就留了。
**追问预备**：subagent 失败怎么办（job 状态可见，主 agent 告知用户并可重试）？为什么 subagent 不直接写库（结果校验收敛到单点；agent 不应理解卡片业务语义）？拆的代价是什么（多一次 LLM 调用的成本 + job 管理复杂度）？

## 4. 记忆形态 【已定方向：AgentScope 双层文件记忆 + 业务库分工；细节待实现验证】

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| A. **AgentScope 双层文件记忆** ✅ | 日志层 `memory/YYYY-MM-DD.md`（只追加）+ 长期层 `MEMORY.md`（LLM 定期合并去重，注入 system prompt） | 开箱即用；可读可审计；与 compaction 联动 | 文件形态，跨实例要挂共享存储 |
| B. 全 DB 记忆 | 记忆条目入 MySQL，检索时查询 | 事务、隔离、易查询 | 注入策略全自建；失去框架联动 |
| C. 外部记忆服务（mem0/ReMe 风格） | 向量化存取，语义召回 | 召回相关记忆而非全量注入 | 多一个服务依赖；单用户场景收益存疑 |

**分工**：agent 运行记忆（对话事实、用户偏好）走 A；**业务事实**（学了哪些知识点、测验成绩、卡片）永远在 MySQL——它们是业务数据不是"记忆"，画像从业务库聚合而非从记忆文件解析。
**追问预备**：记忆和画像什么区别（记忆服务 agent 对话连续性；画像是业务聚合视图）？记忆无限膨胀怎么办（框架有 consolidationMaxTokens 上限 + 归档策略）？

## 5. Checkpoint 存储后端 【待定→执行时按部署形态选】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 本地文件（AgentScope 默认 workspace） | 零配置，开发期最顺 | 单机；容器重建即丢 |
| B. Redis | 快；已有基础设施 | 大快照占内存；持久化策略要调 |
| C. MySQL | 与业务数据同库，事务一致 | 快照是大 JSON，读写较重 |

**建议**：开发期 A，联调后切 B 或 C（AgentScope 的 AgentStateStore 支持三者，切换成本低）。这不是承重决策，选错可改。
**追问预备**：checkpoint 存什么（StateModule 快照：memory + 工具执行上下文；对话 JSONL 是另一条独立轨道）？粒度为什么是知识点边界（语义边界，恢复后上下文自然衔接）？

## 6. RAG 选型（最密集的选择区）

### 6.1 分块策略 【已定 D-011：结构切分为主，token window fallback】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 固定字符窗口 | 最简单 | 字符≠token；切断句子/代码/表格 |
| B. Token window + overlap | 贴合模型预算，参数可复现 | 仍破坏结构 |
| C. **结构感知 + 递归 fallback** ✅ | 按标题/段落/代码/表格切，引用清晰，适合教材 | 依赖解析质量；不同格式要不同 parser |
| D. Semantic chunking（embedding 相似度断点） | 边界可能更语义化 | 额外成本；阈值不稳；可复现性差；论文不支持无条件优于简单切分 |

**为什么 C 不是 D**：D 的收益没有证据支撑且不可复现，C 对教材类材料（有天然结构）收益明确。D 列为评测实验候选而非默认。
**追问预备**：转写文稿没结构怎么办（fallback 到时间窗聚合，见执行方案 4.11）？chunk size 怎么定（先业界常用值 900/120，黄金集上可做 size 扫描实验）？

### 6.2 父子结构 【已定：应用层父子，不用 ES join】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 平铺单层 chunk | 简单 | 精准召回和上下文完整性互相打架：块小了没上下文，块大了召回糊 |
| B. **应用层父子（child 召回，parent_chunk_id 二跳回填）** ✅ | 解耦"召回精准"与"上下文完整"；provenance 保留 child | 二跳多一次查询 |
| C. ES join 字段 | 引擎原生 | 需 routing；global ordinals 内存与查询开销；运维复杂 |

**追问预备**：多个 child 命中同一 parent 怎么聚合（取最高分/加权/去重——待定，黄金集上实验）？为什么只索引 child 的向量（父块向量召回糊，且省 40% 索引体积——待实测验证）？

### 6.3 检索策略 【已定 D-011：BM25 + 向量混合，RRF 融合；rerank 待实验】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. BM25 only | 快、可解释、术语精确匹配强 | 同义改写召回差（"多态"vs"动态绑定"） |
| B. 向量 only | 语义泛化好 | 精确术语/代码符号弱；中文 embedding 质量依赖模型 |
| C. **混合 + RRF** ✅ | 两者互补；RRF 无需调分数权重 | 两路查询成本 |
| D. C + CrossEncoder rerank | 头部精度更高 | 额外模型部署 + 延迟；候选量小时收益待验证 |

**为什么 RRF 不是线性加权**：BM25 分数与 cosine 分数量纲不同，线性加权要调权重且不稳定；RRF 只用排名，免调参、鲁棒。
**追问预备**：RRF 的 k=60 怎么来的（原论文默认值，黄金集上可做敏感性实验）？什么时候值得上 rerank（黄金集显示头部排序是瓶颈时；这是 5.x 阶段实验而非默认引入）？

### 6.4 中文分词器 【已定 D-011：先 baseline 再实验择优，不凭名字选】

| 方案 | 优点 | 缺点 |
|---|---|---|
| standard | 零插件 | 中文退化为逐字匹配，BM25 召回差 |
| SmartCN | Elastic 官方插件，概率分词 | 需装插件重启；自定义能力有限 |
| IK | 自定义词典生态好（可喂领域术语） | 社区插件，版本跟随与升级风险 |

**决策方法本身是亮点**：先建词法 Golden Cases（Java/AI 术语、中英混合、缩写），用 `_analyze` 对比分词结果，再在检索黄金集上比 Recall——"用实验代替名声"这个过程可以直接讲给面试官。
**追问预备**：IK 的 max_word 和 smart 模式差异（细粒度全切 vs 粗粒度歧义消解；索引用 max_word + 查询用 smart 是常见组合，待实验）？

### 6.5 相关性阈值 【已定 D-011：按检索器分离阈值；数值待校准】

| 方案 | 问题 |
|---|---|
| A. 无阈值（旧实现：topK=6 永远返回 6 条） | 不相关也硬凑，污染 context，诱发幻觉 |
| B. 单一全局阈值 | BM25 / cosine / RRF 分数语义不同，一个阈值不可能同时正确 |
| C. **按检索器分离阈值** ✅ | 各自量纲各自选点 | 参数多一点 |
| D. 评测集校准阈值 | 最严谨 | 有黄金集之后才可做——列为 1.16 实验 |

**追问预备**：阈值过滤后一条都不剩怎么办（如实告知"知识库中未找到"，这正是硬禁止编造来源的机制保障）。

### 6.6 Embedding 模型 【已定现状：DashScope text-embedding-v3（1024 维）；可替换点】

| 方案 | 优点 | 缺点 |
|---|---|---|
| **DashScope text-embedding-v3** ✅ | 中文质量好；API 免部署；已接入 | 按量计费；依赖外部服务 |
| bge-m3 自托管 | 免费；dense+sparse 双输出 | 要 GPU/CPU 推理服务，部署与延迟自己扛 |
| OpenAI text-embedding-3 | 生态标准 | 国内访问与合规问题 |

**追问预备**：换 embedding 模型要什么（全量重建索引——这正是索引版本化 + alias 原子切换机制存在的理由，见 B6）。

### 6.7 向量存储 【已定 D-010 隐含：ES 单栈】

| 方案 | 优点 | 缺点 |
|---|---|---|
| **ES dense_vector（BM25 与向量同栈）** ✅ | 一个引擎两种检索，混合查询天然支持；已有运维 | HNSW 性能弱于专用向量库（本项目量级无感） |
| Milvus / Qdrant 专用向量库 | 大规模向量性能好 | BM25 要另一栈，两栈一致性自己扛 |
| pgvector | 与业务同库 | 混合检索能力弱 |

**追问预备**：什么量级才需要专用向量库（千万级向量以上；本项目单用户知识库万级封顶）。

## 7. 知识图谱

### 7.1 形态 【已定 D-009 档位：轻量实体-关系】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 不做（画像只用结构化字段） | 零成本 | 失去"前置知识回溯"这个产品点与讲点 |
| B. **轻量实体-前置关系** ✅ | 支撑补课建议；几百节点 MySQL+BFS 毫秒级 | 不支持复杂推理 |
| C. 图数据库（Neo4j）+ 多跳推理 | 表达力强 | 为几百节点引入一个数据库是简历减分项（过度工程） |
| D. GraphRAG（图谱参与检索增强） | 前沿 | 构建成本高、收益在多文档综合问答场景，与本项目主线（逐知识点学习）不匹配 |

**"为什么不用 Neo4j"是送分题**：几百节点、单一关系类型、两跳以内遍历——邻接表 + BFS 完事。知道什么时候**不**引入组件，比会用组件更值钱。

### 7.2 抽取方式 【已定方向：LLM 结构化输出；校验机制是亮点】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. **LLM 结构化输出抽取** ✅ | 零训练成本；领域适应好 | 会幻觉出不存在的关系 → 必须配校验 |
| B. NER + 关系抽取模型 | 传统可控 | 教育领域无现成模型，标注训练成本远超收益 |
| C. 规则（依赖"前置""基于"等模板词） | 零成本 | 召回极低 |

**校验双保险**（见执行方案 4.9）：实体必须能定位回源文本（防幻觉实体）；前置边与教材章节序一致性检查（自动指标，前置理应大多指向更早章节）。

### 7.3 关系 schema 【建议：固定 2-3 种关系类型】

固定类型（PREREQUISITE / PART_OF）vs 开放抽取（LLM 自由命名关系）：开放抽取会得到"涉及""相关""有助于"这类无法消费的边。**产品只消费"前置"这一种语义，schema 就该只有它**——需求决定 schema，不是反过来。

## 8. 用户画像

### 8.1 构建方式 【建议：规则聚合为主 + LLM 摘要为辅；待实现验证】

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 规则聚合（测验正确率、追问频次、耗时 → 结构化字段） | 可解释、可复算、便宜 | 表达不了"总是混淆 A 和 B"这类模式 |
| B. LLM 定期总结学习行为 | 能捕捉模式化弱点 | 成本；幻觉需抑制；不可复算 |
| C. **混合：规则出数字字段，LLM 出文本摘要（引用数字为据）** ✅ 建议 | 数字可信 + 模式可读 | 两条链路 |

**追问预备**：画像怎么被消费（出题偏向弱项知识点；讲解时对已掌握概念少展开；补课建议结合图谱前置 + 画像弱项）——画像必须有消费方，否则是死数据。

### 8.2 更新时机 【建议：知识点完成时同步更新规则字段，LLM 摘要低频批量】

实时更新（每轮对话）成本高且抖动大；知识点边界更新与 compaction / checkpoint 的节奏天然一致。

## 9. 评测

### 9.1 检索评测集 【已定（简历建议 §四）：合成为主 + 自标注为辅】

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯人工标注 | 质量最高 | 单人产能低 |
| **合成查询（chunk 反向生成，ground truth 天然自带）+ 人工抽检 20%** ✅ | 规模化零标注 | 合成分布偏"文档腔"，需真实感查询补充 |
| 公开数据集 | 现成 | 与你的知识库不匹配，测不了你的系统 |

### 9.2 答案/生成质量 【已定：LLM-as-judge + 自标注校准 + 自一致性检查】

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯人工 | 准 | 不可持续、不可回归 |
| **judge（先在 20-30 条自标注上校准一致率）** ✅ | 可批量、可回归、可进 CI | judge 自身偏好（位置/长度）需缓解 |
| **自一致性检查（模型只看源 chunk 答自己出的题）** ✅ 叠加 | 零标注成本的客观维度 | 只覆盖"可回答性"一个维度 |

**judge 模型选择**：用与生成方**不同**的便宜模型（如生成用 qwen 系、judge 用 DeepSeek），避免同源偏好；低温 + 结构化输出 + 只判可验证维度。
**追问预备**：judge 幻觉怎么办（校准环节就是干这个的：一致率不达标不允许上岗）？为什么不用 GPT-4 当 judge（成本 10 倍+，校准后便宜模型在窄任务上够用——这本身是个可讲的 tradeoff）。

### 9.3 轨迹/流程评测 【已定：模拟学生（LLM persona）批跑】

τ-bench 式做法：LLM 扮演会追问、会答错、会跑题的学生，批量驱动完整会话，测完成率、终止正确性、原地打转率、compaction 节省、崩溃恢复率。**没有真实用户不是遮掩点，方法论本身是展示点。**

## 10. 已定的其余选型（速查）

| 选择点 | 决策 | 一句话理由 | 备选是什么 |
|---|---|---|---|
| ASR | 云端录音文件识别（异步批量）+ 热词表 【D-016】 | 本地 Whisper 的模型/显存/长音频切分与主题无关 | 本地 Whisper；实时流式接口 |
| ES 访问 | 官方 Elasticsearch Java API Client 【D-010】 | 412 行手写裸 JSON 不可维护 | 手写 HttpClient；Spring Data ES（抽象过厚） |
| 复习闭环 | 卡片单向导出 AnkiConnect，不自建调度 【D-005】 | 调度算法不是差异化能力，Anki 复习体验远好于自建 | 自实现 FSRS + 复习 UI；双向同步（一致性黑洞） |
| 用户身份 | header/token 解析 + 单点隔离强制，不做登录产品 【D-003】 | 画像需要真实主体，但整套鉴权偏离主题 | 完整 Security+JWT；纯单用户硬编码 |
| 表结构 | 全部重开新 V1 【D-019】 | 私有仓库无生产数据，兼容迁移零收益 | 从 V7 继续演进 |
| Prompt 管理 | AgentScope Markdown skill 文件 【D-013】 | 文件形态 + 按需加载，不需要版本化系统 | Java 字面量（旧缺陷）；DB + 管理后台（过度） |
| Trace/回放 | 框架 jsonl 全量 trace + 时间线 UI，只展示不重跑 【D-014】 | 重跑模块（工具结果复用 vs 重执行）复杂度高、首版不做 | 自建事件表；可重放 trace |
