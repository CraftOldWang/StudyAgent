# 001 · 全局设计与范围

**日期** 2026-09-01 · **状态** 已确认（六项深度档位由用户定）

## 1. 这份文档定什么

只定**边界**：做几个模块、每个模块拥有什么、不拥有什么、各做到多深。
不定实现。每个模块的内部设计各自另出文档（见 §9）。

判断一项内容该不该进来的标准：它是否服务于四个功能点之一，或服务于「运行时可控、可评测」这个主题。两者都不沾的一律进 §7。

## 2. 一句话定位

一个**可观测、可评测的学习垂类 Agent**：知识库进得来，学习流程跑得完，每一步看得见，改动好没好有数字。

不是通用 Agent 框架。运行时自研的部分只为拿到控制权（配额、预算、恢复、评测），不为覆盖通用场景。

## 3. 模块清单

九个业务模块 + 五个共享层。

| 模块 | 大致内容 | 承载的技术点 | 分量 |
|---|---|---|---|
| `identity` | users 表、身份解析、**数据隔离的唯一强制点** | — | 薄 |
| `ingest` | 上传（分片/续传/去重）、对象存储、解析、清洗、分块、嵌入、索引、管道状态机、MQ、补偿同步 | 分块策略 | 大 |
| `rag` | 检索策略（BM25/向量/RRF/父子）、相关性阈值、查询改写、**以工具形式暴露** | RAG as tool、检索策略 | 中 |
| `agent` | **通用运行时**：Loop、Context、工具与治理、记忆、checkpoint、trace、子 agent 委派、prompt、codec | Loop 与批量调用、工具治理、context 压缩、文件记忆、checkpoint、轨迹、多 agent | 承重 |
| `learning` | 学习垂类流程：学习计划、知识点生命周期、讲解/答疑/测验/卡片各为一种 skill、知识点完成后 compact | 委派的使用方 | 中 |
| `review` | Anki 卡片、单向导出 / AnkiConnect adapter | — | 薄 |
| `profile` | 用户画像、长期记忆、轻量知识图谱 | 长期记忆 | 中 |
| `eval` | RAG 评测、轨迹评测、LLM as judge、黄金集 | RAG 评估、轨迹评测、judge | 承重 |
| 前端 | 知识库、学习会话、trace 时间线、画像 | — | 中 |

共享层：`config` / `common` / `model` / `mapper` / `algo`（见 D-001）。

**承重的是 `agent` 与 `eval`**——差异化在这两块。`ingest`/`rag` 工程件可复用所以便宜。`identity`/`review` 刻意做薄。

## 4. 依赖方向

```text
identity  ←  所有模块（隔离条件）
ingest    →  rag        （供数据：索引）
agent     →  rag        （当工具用）
learning  →  agent      （跑在运行时上）
learning  →  profile     （产出学习信号）
review    ←  learning   （卡片来源）
eval      →  agent, rag （观察它们，不被它们依赖）
```

两条硬约束：

- **`agent` 不依赖 `learning`。** 运行时不认识「知识点」「测验」这些概念。这条一破，「通用运行时 + 垂类流程」的说法就不成立了。
- **`eval` 只被依赖方向的下游读取，不进请求路径。** 离线批量。

## 5. 各模块边界

### identity
拥有：`users` 表；从请求头 / API token 解析身份；隔离条件的单点注入。
不拥有：注册、登录、密码、找回、RBAC。（D-003）

### ingest
拥有：上传接口与分片/续传/去重、对象存储适配、格式解析、文本清洗、分块、嵌入调用、索引写入、管道状态机与失败可见性、MQ 投递、Canal 补偿。**含云端 API 形式的音视频 ASR。**
不拥有：检索。索引写入是它的终点，读是 `rag` 的事。
**注意**：工程件（分片续传/去重/S3/MQ/Canal）复用旧实现；分块与清洗**策略**重新设计（修正 D-002）。

### rag
拥有：检索策略与融合、相关性阈值、查询改写、结果装配与出处、以工具形式对 `agent` 暴露。
不拥有：索引构建、嵌入模型选型的落地（属 `ingest`）；评测（属 `eval`）。

### agent
拥有：Loop 与终止控制、批量工具调用、消息列表与 token 预算与分层压缩、工具注册与治理（体积上限/写入配额/超时/重试）、文件形式记忆、session 与 checkpoint、trace（traceId/事件/回放读取模式）、子 agent 委派、prompt 模板与版本、结构化输出 codec。
不拥有：任何学习领域概念。工具由外部注册进来，它只管治理与执行。

### learning
拥有：学习计划的生成与推进、知识点生命周期、讲解/答疑/测验/卡片各自作为一种可委派的 skill、知识点完成后触发 compact、把信号投给 `profile`。
不拥有：Loop、压缩、trace 这些机制本身——它是使用方。

### review
拥有：卡片模型、单向导出到 Anki（AnkiConnect adapter）。
不拥有：调度。FSRS 暂不进主流程（D-005）。后续可能反向拉 Anki 统计，未定。

### profile
拥有：画像字段、长期记忆、**轻量实体-关系图谱**（从学过的知识点抽实体与前置关系，可视化即可）。
不拥有：图数据库、多跳推理。先出一版，再看是否优化。

### eval
拥有：RAG 检索评测（Recall@K 多策略对比）、答案质量评测（LLM as judge）、轨迹评测（工具选择/终止/绕圈）、人工标注黄金集与 judge 一致率校准、回归门槛。
不拥有：在线打分、请求路径内的任何逻辑。

### 前端
拥有：知识库管理、学习会话、**trace 时间线视图**、画像展示。
不拥有：编排配置、prompt 编辑等运营向功能。够用即可。

## 6. 六项深度档位（用户已定）

这六项每项都有「不做／中档／重做」三种可能，是范围失控的主要来源，所以单列。

| # | 项 | 定的档位 | 理由 |
|---|---|---|---|
| 1 | `agent` 与 `learning` 是否分开 | **分开** | 不分则「通用运行时 + 垂类流程」的说法不成立，整个项目退化为「写死了学习流程的程序」 |
| 2 | 音视频 ASR | **云端 API** | 本地 Whisper 要处理模型、显存、长音频切分，与主题无关且极易吃掉数周 |
| 3 | 知识图谱 | **轻量实体-关系** | 能支撑「前置知识回溯」这一个讲点即够；图库与多跳推理性价比低 |
| 4 | Trace 回放 | **时间线 UI + 从 checkpoint fork 重跑** | 时间线满足功能点 3；fork 复用 checkpoint，不额外造机制 |
| 5 | 多 agent | **仅扇出委派** | 多角色协商是另一个量级，且不服务任何功能点。judge 归 `eval`，不算协作拓扑 |
| 6 | 模块投入配比 | `agent`/`eval` 承重；`ingest`/`rag` 复用工程件重做策略；`identity`/`review` 薄；`profile` 先一版 | 把预算压在差异化的两块上 |

第 4 项留下一个待定：**重跑时工具结果复用记录还是重新执行**。

- 复用记录（确定性重放）：只换 prompt/模型，能干净证明改动生效。代价是工具结果需全量落库，体积大。
- 重新执行：真跑一遍，但索引可能已变，结果不可比。适合验证修复。

大概率两种都要，需定默认。另外**模型不确定性来源必须落库**：temperature、seed（provider 支持时）、模型版本——否则「重跑结果不同」无法区分改动生效与模型抖动。这一项并入 D-Q07 / D-Q11 的联合设计（见 §9）。

## 7. 明确不做

写进文档是为了防止范围蔓延。后续任何 agent 或讨论提出这些，直接引用本节拒绝。

- 注册 / 登录 / 密码 / 找回 / RBAC（D-003）
- 自建 FSRS 调度与复习 UI（D-005）
- 多租户
- Skill 市场、插件热加载
- 图形化流程编排
- Anki 双向同步（只单向导出）
- 真流式语音输入
- 多角色 agent 协商（Coach / Teacher / Critic 那类拓扑）
- 通用 Agent 框架化（不追求脱离本项目复用）

## 8. 简历与面试口径

**不要以「自研 Agent Runtime」领衔。**那句话邀请「和 LangGraph 比怎么样」这个必输的比较。

以可控与可评测领衔，例如：

> 学习垂类 Agent，重点在运行时的可控与可评测：接管工具执行循环以实现工具配额与结果体积治理；分层 context 压缩在固定 window 下支撑长会话；轨迹按 traceId 全量落库并支持从 checkpoint fork 重跑；检索策略 A/B（Recall@K）+ LLM-as-judge 答案质量回归。

自研运行时的**唯一理由**是：用框架内置循环时，下面四个问题一个都答不出来。

1. 模型一次返回 200 张卡，往库里写几条？（工具由框架执行时插不进配额）
2. 单次工具结果 2400 字原样进 prompt，第 8 轮 window 爆了怎么办？（context 预算）
3. run 在第 7 步崩了，重启从哪继续？（checkpoint）
4. 这次检索比上次好在哪，用哪个数字证明？（评测）

判断一条内容值不值得写：**能否被追问三层**。「怎么压缩的」→「分层，工具结果先降级为摘要，再丢历史轮次」→「为什么先降工具结果」→「占比最大，且原文可从 trace 回查」。

## 9. 后续详细设计文档顺序

顺序由依赖决定，不由兴趣决定。

1. **002 · Agent 运行时内核**——Loop 归属、context 预算与分层压缩、工具治理、trace 事件模型、checkpoint 与回放读取模式，**一份文档一起定**。它们互锁：Loop 归属决定治理是否可能；Loop 的轮次边界决定 trace 的记录单位；记录单位决定 checkpoint 能从哪恢复；context 预算决定 trace 必须快照什么。对应 D-Q03/Q04/Q05/Q07/Q11。
