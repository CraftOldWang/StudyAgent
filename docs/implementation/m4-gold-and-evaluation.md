## 测量口径

`scripts/run-rag-evaluation.py` 通过 `/api/knowledge-bases/{id}/search` 批量调用，保留请求、完整响应、trace、耗时、JAR/Git/脚本/数据/配置指纹。调用前检查实际索引的文档集合、切块版本与 embedding 模型。

- annotated-evidence Hit@5：前五个子块中，至少一个包含与文档 SHA 对应的完整标注证据。
- MRR@10：前十个子块的首个标注证据命中倒数排名。
- Context evidence hit：4096 token 正文预算内的实际上下文，是否包含标注证据。父块回填单独使用这一指标，原始子块排名应与 RRF 相同。
- 匹配仅做 NFKC、空白与大小写规范化；不把不同文档中的相同文本误算为相关。同课程其他文档有相同完整证据时提前扩展标签。
- 这是**标注证据命中率**，标签并未覆盖全部语义等价答案。长引用必须完整落在一个块中；该限制会影响小块结果，报告保留这一局限。资料不足题另测回答/拒答，不能用检索是否为空替代。
- 用实际 provider usage 计算每个配置的逻辑子块 embedding token 总量；命中缓存时回溯原调用成本，避免把后执行配置误判为更省。另列唯一内容成本和实际增量账本，两者不混用。

评分脚本的 3 项独立合成测试通过，覆盖文档范围、Unicode/空白、Rank 6 边界、部分引用与上下文命中。结构 800/80 初始开发组真实 API 20/20 成功：算法 Hit@5 0.9，OS 1.0，宏平均 MRR@10 0.78917；12 份开发课程文档有 40 个父块、140 个子块，逻辑 embedding token 81,389。这只是选型观测。

后续审查发现初始 800/80 所在索引还含烟测和编译原理文档，其结果移入 `.eval/runs/dev-structured-800-80-preflight/`，不用于最终选型。因为评分使用分片的词项/文档统计，知识库过滤不足以消除索引总体不同带来的混淆（[Elastic Search API](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/search-search.html)）。已要求各开发配置索引仅含同样 12 份原件、1 个主分片，评分脚本增加全索引数量检查；800/80 用新的独立索引复测。原始记录和初步大小选择记录均保留，问题集未改动。
