# 400 MB 上传对照报告

测量日期：2026-09-09。本机生产上传 API 对照，原始结果和统计为 [upload-comparison-v1.json](../evidence/m6/upload-comparison-v1.json)，脚本为 `scripts/benchmark-upload.py`、`scripts/summarize-upload-benchmark.py`。

## 结论

相同 4 并发条件下，400,000,000 字节文件的端到端上传中位数由 **35.048 s 降至 17.833 s，减少 49.1%**，两组各 5 次全部成功。完成接口中位数由 13.739 s 降至 2.073 s；服务端原生合并阶段中位数为 0.264 s，仍进行完整文件 SHA-256 校验。

这里比较的是上传实现整体改动，包含原生合并、短事务与分片状态写入调整；不是只改变一个 S3 API 的消融实验。数字限定为当前 Windows/Docker 本机环境，不外推公网、弱网或不同硬件。

## 固定条件

- 样本：固定种子的 400,000,000 字节随机字节，SHA-256 `611c3ebab2a693c976d55c24d3d17143097e29b9be8962765e2af1f6e4ce2963`；测试接口使用 PDF 扩展名，异步消费者停用，因此不代表 PDF 内容解析验收。
- 分片：8,388,608 字节，共 48 片；串行和 4 并发各 5 次，奇偶轮反转两组顺序，旧/新实现分批部署。
- 客户端：同一 Python requests 脚本，Windows loopback 到 Docker 的 8080；每次先本地完整计算哈希。新知识库隔离每次性能样本，均未命中秒传。
- 服务：同一 MySQL、Redis、RustFS、RocketMQ 容器；JVM `-Xmx384m`，Docker 总可用内存约 3.818 GiB。其它既有本地服务未关闭。
- 数据隔离：MySQL `study_agent_upload_eval`、Redis DB 2、RustFS `study-agent-upload-eval`、专用 MQ topic。真实 producer/broker 保留，测试消费者经配置禁用。STORED 文档仍会被周期补偿任务重新入队，不调用解析或模型；两批均保留此配置。
- 起止：客户端哈希开始 → 初始化 → 分片请求 → 查询完整性 → complete 返回。包括数据库提交和首次 MQ 发送；不含建库、样本生成、解析、embedding 和索引。

## 各组统计

时间单位为秒，各列分别求中位数，不应按列相加。

| 实现 / 并发 | 成功数 | 总耗时中位数 | 总耗时范围 | 分片传输中位数 | 完成接口中位数 | 服务端合并中位数 | 服务端校验中位数 |
|---|---:|---:|---|---:|---:|---:|---:|
| 原实现 / 1 | 5/5 | 41.103 | 31.068–45.823 | 27.661 | 12.759 | 9.070 | 2.623 |
| 原实现 / 4 | 5/5 | 35.048 | 23.839–35.818 | 20.397 | 13.739 | 9.286 | 3.400 |
| 原生 / 1 | 5/5 | 22.816 | 20.117–28.013 | 20.692 | 1.323 | 0.219 | 0.775 |
| 原生 / 4 | 5/5 | 17.833 | 9.615–19.746 | 14.911 | 2.073 | 0.264 | 1.308 |

原实现先从对象存储读所有临时分片校验哈希，再读取一次并经应用重新上传最终对象。新实现保存 S3 uploadId 与每片 ETag，调用对象存储完成合并，再读取完整对象做 SHA-256 校验；不再经应用重新传输整份最终文件。同时，分片写入不再逐片遍历全部 Bitmap 位、回写整个会话快照，完整哈希读取缓冲从 8 KiB 调整为 64 KiB。上述因素均可能影响耗时，不能把所有变化只归因于“Bitmap 加速”或“原生合并”。

## 结果边界与简历口径

样本量为每组五次，存在明显运行波动，不报告高分位延迟或普遍提升。没有人为删除首次较快或后续较慢的样本。旧/新分批执行，缓存、后台任务与宿主机调度可能影响差异；这是一份可复现的工程实测，不是隔离所有硬件因素的实验室评估。

可引用口径：**“实现原生分片上传与断点续传，持久化 uploadId/ETag 并结合 Redis Bitmap 恢复进度；在本机 400 MB、4 并发测试中，上传总耗时中位数由 35.05 s 降至 17.83 s（每组 5 次）。”** 最终简历是否保留全部限定文字，应在收尾时与其它五条一起压缩，但不能替换为未测得的“20 s → 9 s”。
