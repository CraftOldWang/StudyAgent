# Phase 1.7-1.8 · Parent 聚合与检索编排实现记录

- 关联任务：GitHub Issues #15 / #16

## 范围

本批次在新 `rag/retrieval` 模块内完成 parent 二跳和 BM25、VECTOR、RRF、PARENT 四种模式的统一编排。不生成 LLM 答案，不做 query rewrite、相关性阈值实验、Controller/旧消费者迁移、fallback 或重试。

## 已执行选择

- `ParentAggregator` 从 child 命中的 `parentChunkId` 去重得到批量查询集合，通过官方 Elasticsearch client 和读别名一次查询 parent。
- parent 查询同时强制 `user_id`、`knowledge_base_id` 两个服务端 scope filter，并附加 `chunk_type=PARENT` 与 `chunk_id terms`；模型不参与权限参数。
- parent 内容替换 child 内容时，继续保留 child 的 `chunkId`、`parentChunkId`、分数和检索来源。child 没有 `parentChunkId`，或引用的 parent 未查到时，明确原样返回 child，不伪造 parent 内容。
- `RetrievalService` 用 `RetrievalMode` 编排 BM25、VECTOR、RRF、PARENT。BM25/Vector 接收的是 `candidateLimit`，最终 `topK` 只在服务编排出口截取；PARENT 模式先完成双路 RRF，再批量取 parent。
- RRF 固定 `k=60`，直接复用 `algo/rrf/RrfRanker`。因现有算法 API 使用 `Long chunkId`、新索引契约使用 `String chunkId`，编排层为一次融合建立无碰撞的顺序 surrogate ID 与反向映射，没有复制第二套 RRF 算法。
- RRF 输出统一映射为 `RetrievalHit`，strategy 为 `RRF`；parent 聚合属于上下文装配，因此不覆盖 child 的检索 strategy provenance。

## 测试覆盖与验收

- parent 查询使用读别名、一次 terms 批查、user/knowledge-base 双重过滤，并保留每个 child provenance。
- 无 parent 引用和 parent 文档未命中均返回原 child；无引用时不访问 Elasticsearch。
- BM25、VECTOR、RRF、PARENT 四种模式分别覆盖；候选规模传给单路检索器，统一出口执行 `topK`。
- RRF 测试覆盖交叉命中的排名与 `k=60` 分数，PARENT 测试证明聚合发生在最终 topK 之前。

独立验收前静态审查指出 `ParentAggregatorTest` 存在 Mockito 嵌套 stubbing；测试改为先构造响应再交给 `thenReturn` 后，#12-#16 retrieval 定向测试 14/14 PASS，`mvn compile` PASS，未参与实现的 subagent 独立验收判定通过。

Windows 全量测试的唯一 error 来自 Elasticsearch loopback 环境；后续 Linux 真实 Elasticsearch 8.15.3 已验证 #9-#11 的建索引、alias、mapping 与写入运行链。该结果不扩张为 #15/#16 的真实检索集成验收。#15/#16 当前为“独立验收通过/待交付”，本文不声明已提交、已关闭 Issue 或已同步 Project。
