## 核心流程

`DocumentPipeline` 提供两种 claim 入口：常规 `process` 允许 `PENDING/FAILED`，`processPending` 只允许 `PENDING`，供后续 MQ/显式调用与 Canal 切换时分别接线。取得 claim 后依次执行：

`PARSING → CHUNKING → EMBEDDING → INDEXING → COMPLETED`

- 使用现有 `ObjectStorageService.getObject` 和 `DocumentTextParser.parse`，不复制 S3 或 Tika 实现。
- 使用 `StructuredChunker.parentChunks` 生成父块，再用同一个本地 token 口径的 `TokenWindowChunker.childChunks` 在父块内生成子块，保证 child 的来源坐标落在对应 parent 坐标内。
- `parser_version=tika-3.3.0`，`chunker_version=structured-jtokkit-cl100k-v1`。
- `content_hash` 是完整 SHA-256；业务 `chunk_id` 严格按 `SHA-256(UTF-8(documentId + chunkerVersion + chunkType + chunkIndex + contentHash))` 生成 64 位小写十六进制。
- embedding 使用现有 `EmbeddingService`；ES `embedding_model` 从当前 `AiModelProperties.embedding.model` 读取，不使用独立常量。
- ES 文档的 `_id` 使用业务 `chunk_id`；`user_id/knowledge_base_id` 直接来自已 claim 的 `Document`，一次 bulk 成功后才写 `indexed_at` 并推进 `COMPLETED`。

## 事务与失败边界

`DocumentPipeline` 本身没有大事务。`DocumentPipelinePersistence` 提供短事务：

- 条件 claim 并推进 `PARSING`；
- 记录 parser 版本并推进 `CHUNKING`；
- 原子替换 chunks、记录 chunker 版本并推进 `EMBEDDING`；
- 更新 chunk embedding 状态并推进 `INDEXING`；
- bulk 成功后写 `indexed_at` 并推进 `COMPLETED`。

每次推进都带 expected status 条件，未取得状态所有权时明确失败。任一阶段异常由 `markFailed(REQUIRES_NEW)` 写 `FAILED`，`error_message` 格式为 `<STAGE>: <原始错误摘要>`。

失败重试重新生成相同业务 chunk ID，并通过 ES 相同文档 ID 覆盖；本任务不新增按 document 删除 ES、重试框架、向量缓存或 `token_count` 持久化。
