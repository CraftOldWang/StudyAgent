## 实现边界

`RrfRanker` 接收各路已经按相关性排序的候选列表。候选项在某一路的排名从 1 开始，固定配置 `k=60` 时，该路贡献为：

```text
1 / (60 + rank)
```

同一 `chunkId` 出现在多路结果中时只产生一个融合项，各路排名贡献相加；`sourceScores` 按来源保留原始分数，供后续调试和评测解释使用。不同检索器的原始分数不参与融合，避免直接比较量纲不同的 BM25 分数与 cosine 相似度。

算法返回全部融合结果，不负责截取 topK。Issue #14 的“融合后返回 topK”验收口径落在检索编排边界：现有消费者继续负责截取，后续由 Issue #16 / Phase 1.8 `RetrievalService` 统一收口。这样既保留 RRF 纯算法的完整排序能力，也不把请求级 topK 参数引入 `algo`。

## 稳定排序

融合结果只按 RRF 总分降序排列。Java Stream 的对象排序是稳定排序，因此总分相同时保留候选首次出现的顺序；不再按 `chunkId` 二次排序，避免将与相关性无关的数据库标识引入排序偏好。

## 测试范围

`RrfRankerTest` 覆盖：

1. `k=60` 的精确排名公式；
2. BM25 与向量结果中相同 `chunkId` 的合并及来源原始分数；
3. 无召回结果；
4. 单路召回；
5. 融合总分并列时按首次出现顺序稳定排序。

实际验收证据：#12-#16 retrieval 定向测试 14/14 PASS，`mvn compile` PASS；Windows 全量测试的唯一 error 属于 Issue #9-#11 的 Elasticsearch loopback 环境限制。后续 Linux 真实 Elasticsearch 8.15.3 已验证 #9-#11 的建索引、alias、mapping 与写入运行链；Issue #14 已由未参与实现的 subagent 独立验收并判定 PASS，已通过实现 commit `e38439a` 与文档 commit `57c1895` 交付，Issue #14 Closed / Project Completed。
