## 实际变更

### 1.1 Java API Client

- 统一版本 `elasticsearch-java=8.15.3`，与 docker-compose 的 Elasticsearch 版本一致。
- `ElasticsearchConfiguration` 创建 `ElasticsearchTransport` 与类型化 `ElasticsearchClient` Bean；transport 关闭时释放底层 REST client。
- `ElasticsearchProperties` 明确区分 physical index、read alias、write alias 与向量维度。

### 1.2 chunks-v1

- 应用启动时若 `chunks-v1` 不存在，使用官方 client 一次创建完整 mapping 以及 `chunks-v1-read`、`chunks-v1-write`；write alias 显式设置 `is_write_index=true`。
- 已有物理索引只补缺失 alias，不重建索引、不修改已有 mapping，避免启动过程隐式改变已有数据契约。
- 经用户批准的 ES 隔离补充在 mapping 中增加 `user_id` keyword；其余字段严格采用技术设计方案：三个资源 ID、父子关系、类型与序号、`content` 的 standard/keyword 双字段、内容哈希、1024 维 cosine 向量、分块/嵌入版本与创建时间；未混入 legacy 展示字段。

### 1.3 索引写入

- `ElasticsearchIndexer` 的单条写入使用官方 `IndexRequest`，bulk 写入使用官方 `BulkRequest`，统一写 `chunks-v1-write`。
- ES 文档 `_id` 使用业务 `chunk_id`，重投时保持覆盖语义；写入前校验 embedding 维度。
- `ElasticsearchChunkDocument.userId` / `knowledgeBaseId` 必须由服务端已验证的 V2 `Document` scope 提供；Indexer 在请求发出前拒绝 null/blank，禁止默认用户值。MySQL `document_chunks` 不恢复这两个冗余字段。
- bulk 响应含 item error 时明确失败并保留失败 ID/原因，不重试、不降级。
- legacy `ElasticsearchChunkIndexer` 删除建索引和单条写入职责，仅保留 Phase 1.4-1.8 尚未迁移的读取/删除能力，并改读 `chunks-v1-read`；clean cutover 后不保留旧写入桥。
- clean cutover 的索引写入统一由 V2 `DocumentPipeline` 提供 `Document` scope 和 chunk 字段，不从旧 `DocumentChunk` 补 user/KB 或版本值；评测需要 scope 时经 `document_chunks.document_id → documents` 关联取得。
