# Phase 1 / 1.9-1.10 结构分块与 token fallback

- 关联任务：[Issue #17](https://github.com/CraftOldWang/StudyAgent/issues/17)、[Issue #18](https://github.com/CraftOldWang/StudyAgent/issues/18)
- 决策依据：[ADR-0002](../../adr/0002-phase1-chunk-contract.md)
- 状态：实现完成，待 Phase 1 批次测试与独立验收

## 固定 token 口径

项目固定使用 `com.knuddels:jtokkit:1.1.0` 的 `CL100K_BASE` encoding，调用 `countTokensOrdinary` 在本地确定性计数。`StructuredChunker`、`TokenWindowChunker`、`ChunkSegment.tokenCount` 与测试共用同一个 `TokenCounter`，不再使用字符数估算。

该数值只定义 StudyAgent 当前 `chunker_version` 的分块口径，不宣称等于 DeepSeek 或其他模型供应商的计费 token。未来如调整 jtokkit 版本或 encoding，必须提升 `chunker_version`，重新分块、索引并运行检索回归。

## 数据契约与坐标

- `ChunkSegment(content, tokenCount, sourceLocation)` 是两级 chunker 的统一结果。
- `SourceLocation(startInclusive, endExclusive, headingPath)` 使用解析器输出文本的 Java `String` offset，即 UTF-16 `[startInclusive, endExclusive)`。
- 结构切分与 fallback 都保留原文精确 substring，不做 trim、空白折叠或换行归一化；窗口边界不会切断 Unicode surrogate pair。
- `headingPath` 由 ATX 标题层级生成，并随 fallback 子窗口原样传递。

Phase 1 不增加页码、PDF 坐标或 ASR 时间戳。

## 结构优先算法

`StructuredChunker` 使用最小确定性 Markdown 行扫描器，按以下原子结构产生 segment：

1. ATX 标题；
2. 由空行分隔的段落；
3. 连续 Markdown 列表项；
4. 反引号或波浪号围栏代码块；
5. 带标准分隔行的 Markdown 表格。

普通结构块不因尚未达到窗口上限而跨结构合并。只有单个结构块超过所选上限时才交给 `TokenWindowChunker`；child 固定 900/120，parent 固定 2400/240。窗口结束与下一窗口起点都用同一 `TokenCounter` 计算，重叠不超过指定 token 数。

这不是完整 CommonMark AST，也不提前加入 Setext 标题、嵌套列表语义树或自适应窗口；这些不属于当前最小 V1。

## 旧入口与后续迁移

`DocumentProcessingService` 的迁移属于 Issue #19，本任务不修改该消费者。现有 `TextChunker` 暂时保留原静态签名，仅把调用委托给 `StructuredChunker` 并投影为 `List<String>`；旧字符窗口与边界吸附逻辑已移除，不存在第二套核心分块算法。旧 pipeline 尚未读取 `ChunkSegment.tokenCount` 与来源坐标，其接入和旧 `estimateTokenCount` 的删除留给 Issue #19；届时也可删除该兼容入口。

## 测试范围

- CL100K_BASE 的固定计数与 ordinary special-token 文本处理；
- Markdown 标题路径、段落、列表、代码块、表格边界；
- 超长结构块 fallback 的 token 上限与重叠口径；
- Unicode code-point 安全切分、原文 offset 与 headingPath 保留；
- 非法窗口参数及旧 `TextChunker` 的薄委托。

按 Phase 1 批次规则，本轮只编写测试，不运行 `compile` 或测试；最终状态由完整批次统一验证和未参与实现的 subagent 独立验收后更新。
