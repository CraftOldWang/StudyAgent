# Phase 3 / 3.7 Context compaction

## Scope

The production `HarnessAgent` now uses AgentScope 2.0.1's real
`CompactionConfig` through `HarnessAgent.Builder.compaction(...)`. The policy
compacts when the reasoning context exceeds six messages and keeps the two
most recent messages. The summary prompt asks the model to preserve the
learning target, current knowledge-point status, discoveries/misconceptions,
and remaining plan without inventing facts.

The configuration deliberately disables `flushBeforeCompact` and
`offloadBeforeCompact`: this task only validates in-memory context replacement;
it does not introduce persistence or a second memory implementation.

The summary prompt contains AgentScope's required `{messages}` placeholder.
Without it, the framework sends the custom instructions but not the history
being compacted.

## Runtime boundary

The local AgentScope 2.0.1 JAR exposes `CompactionMiddleware.onReasoning(...)`
and `ConversationCompactor.compactIfNeeded(...)`, but no public method on
`HarnessAgent` or `CompactionMiddleware` for an application-defined
knowledge-point-completed event. This implementation therefore provides the
verified message-count trigger boundary. Wiring that boundary to the learning
state transition remains a separate learning-flow task; no private API or
guessed callback is used here.

## Verification

`AgentScopeCompactionTest` builds the production configuration with a local
recording `Model`, makes four fixed calls, and verifies that:

1. the real Harness compaction hook is installed;
2. the summary model receives the fixed target, status, discovery, and plan
   facts;
3. the compacted agent context contains the model-produced summary with those
   facts after the configured boundary is crossed.

The test never calls a remote provider and uses a temporary state-store home
and workspace.
