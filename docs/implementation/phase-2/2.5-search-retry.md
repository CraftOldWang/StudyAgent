# Phase 2 / 2.5 `knowledge_search` 业务级重试

## 范围与语义

- 只对工具名严格等于 `knowledge_search` 的调用生效。
- 首次失败后最多重试 3 次，因此一次业务调用最多执行 4 次检索。
- 只识别异常 cause 链中的明确 timeout 类型：`TimeoutException`、
  `SocketTimeoutException`、`HttpTimeoutException`。不根据异常消息猜测超时。
- 非 timeout 失败立即原样抛出；其他工具即使发生 timeout 也不重试。
- 不引入退避、配置项、注解、反射或通用重试框架。

## AgentScope 2.0.1 扩展点核对

本机 2.0.1 的 `MiddlewareBase` 公开 `onAgent`、`onReasoning`、`onActing`、
`onModelCall` 四类回调。`onActing` 接收一批 `ToolUseBlock`，其 `next` 包围的是
整次 acting；用它重试会重新执行同批其他工具，不能安全地只重试
`knowledge_search`。

`Toolkit` 公开工具注册及 `callTool` / `callTools`，但没有公开的单工具执行
middleware/decorator 注册点。因此本任务没有把重试塞进现有
`ToolGovernanceInterceptor`，而是新增普通 Spring 组件
`KnowledgeSearchRetryExecutor`。后续任务 2.1 实现 `KnowledgeSearchTool` 时，由该工具
显式调用 `execute("knowledge_search", retrievalCall)`，从而让重试范围停留在真实检索
执行边界，不重放同批其他工具。

## 类型传播边界

执行器会沿 cause 链识别 timeout，但不会把仅含“timeout”字样的业务异常视为超时。
因此后续工具接线必须保留底层 timeout 类型或 cause；如果检索适配层把异常转换为
不带 cause 的普通业务异常，本组件会按非 timeout 处理，不会误重试。工具的模型可见参数
只保留 `query`；user/单一 knowledge base scope 由服务端从已验证的 `RuntimeContext` 注入，
不参与重试参数。
