# 0.6 MyBatis 数据隔离实现记录

## Scope

- `CurrentUserContext` 以请求作用域保存 `IdentityResolver` 从当前 `HttpServletRequest` 解析出的 `userId`。
- MyBatis 单例配置通过 Spring 的请求作用域代理读取当前 `userId`。
- 直接注册 MyBatis-Plus 官方 `TenantLineInnerInterceptor`，由 JSQLParser 为 SELECT 查询注入 `user_id` 条件。
- 测试覆盖普通 SELECT、已有 WHERE、带别名 JOIN、`users` 排除、缺失/非法 header 以及两个顺序请求的身份隔离。

## 已采用方案与依据

- 使用 `HttpServletRequest -> IdentityResolver -> @RequestScope CurrentUserContext`。请求作用域让单例拦截器读取当前请求身份，而不是把身份保存在单例或线程静态变量中；连续请求由各自的作用域实例承载，不共享 `userId`。
- 使用 MyBatis-Plus 3.5.16 的 `MybatisPlusInterceptor` + `TenantLineInnerInterceptor`，并显式依赖 `mybatis-plus-jsqlparser-4.9:${mybatis.plus.version}`。这是当前已确认的持久化版本和官方 SQL AST 改写机制，避免 AOP 漏掉查询入口，也不做脆弱的 SQL 字符串拼接。
- 设计文档中的 `DataIsolationInterceptor` 是职责名。本实现没有创建无行为包装类；实际 Spring Bean 是 `DataIsolationConfiguration` 提供的 `MybatisPlusInterceptor`，其中直接注册官方 `TenantLineInnerInterceptor`。
- 默认 fail-closed：除 `users` 外所有 MyBatis SQL 表都进入 `user_id` 注入。`users` 是当前唯一忽略表，因为该表自身没有 `user_id` 列；本任务不提供后台 bypass 或系统身份。
- 缺失或非法 `X-User-Id` 继续沿用 0.5 的自然 `NumberFormatException` 语义，不新增默认身份、业务异常或 HTTP 错误响应协议。

## 能力边界

MyBatis-Plus 官方 `TenantLineInnerInterceptor` 不只重写 SELECT，也实现了 UPDATE、DELETE 和 INSERT 的租户字段处理。然而 Phase 0 / 0.6 的完成声明和本任务测试只证明 SELECT 行过滤，不能据此宣称已经完成写入授权。写入场景仍需要以后结合真实 Mapper、事务边界和越权用例单独验收。

本任务不修改旧 Controller、Service、Mapper、历史 `DEFAULT_USER_ID`、V1 迁移、错误响应协议或 Elasticsearch 隔离。
