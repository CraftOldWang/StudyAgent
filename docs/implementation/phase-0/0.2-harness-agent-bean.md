# Phase 0 / 0.2 生产 HarnessAgent Bean

- 关联任务：Issue #2
- 状态：实现完成，待批量验收
- 范围：只把已经由 0.3 与 0.4 提供的生产依赖装配为 Spring 管理的 `HarnessAgent`。

## 依赖与装配

- `AgentScopeWorkspaceConfiguration` 提供命名 `Path` Bean `agentScopeWorkspacePath`，并在返回前创建目录。
- `AgentScopeModelConfiguration` 提供命名 `Model` Bean `agentScopePrimaryModel`。
- `AgentScopeModelProperties.maxRetries` 提供已确认的重试值 `1`。
- `AgentScopeAgentConfiguration` 使用两个精确 `@Qualifier` 注入生产 `Model` 与 workspace `Path`，随后调用 AgentScope 2.0.1 已验证的 `HarnessAgent.builder().model(...).workspace(...).maxRetries(...).disableSubagents().build()`。

`Model` 与 `Path` 都可能在后续出现同类型 Bean，因此这里不依赖 `@Primary` 或参数名推断。fallback 没有配置：不注入 fallback `Model`，也不调用 `fallbackModel(...)`，不会因两个 provider 同时位于 classpath 而自动降级。

## AgentScope 2.0.1 API 依据

本机 2.0.1 JAR 的公开签名确认：

- `HarnessAgent.builder()` 返回 `HarnessAgent.Builder`；
- Builder 公开 `model(Model)`、`workspace(Path)`、`maxRetries(int)`、`disableSubagents()`、`fallbackModel(Model/String)` 与 `build()`；
- `HarnessAgent.getModel()` 与 `getWorkspaceManager().getWorkspace()` 可核对生产依赖；
- `HarnessAgent.getDelegate().getModelConfig()` 返回带 `maxRetries()`、`fallbackModel()` 的 `ModelConfig`。

Builder 没有要求本任务决定其他必选参数，因而没有增加名称、系统 prompt、工具、状态存储、memory、trace、权限或 Controller 配置。workspace 仍与默认 `${user.home}/.agentscope/state/<agentId>` state store 分离。

Phase 0 没有 subagent 需求，因此显式关闭全部 subagent middleware，避免 Harness 构造进入 `buildSubagentsMiddleware` 后创建 `WorkspaceTaskRepository -> AgentProtocolTaskClient -> JDK HttpClient`。此前只调用 `disableDynamicSubagents()` 的判断已被动态构造验证推翻：该调用仍会进入上述构造链，不能满足 Phase 0 的隔离目标。`disableSubagents()` 不影响核心 Harness call、Model、workspace 或重试配置。Phase 3 按对应任务启用 subagent 时删除该调用，并按届时的 subagent 声明与 transport 需求独立实现和验收。

## 测试范围

`AgentScopeAgentConfigurationTest` 提供两个 `Model` Bean 与两个 `Path` Bean，验证：

1. Spring 容器只构造一个生产 `HarnessAgent` Bean；
2. 精确 qualifier 选中 `agentScopePrimaryModel` 与 `agentScopeWorkspacePath`；
3. `maxRetries` 从类型化配置传入且为 `1`；
4. `fallbackModel` 保持为空；
5. stub `Model.stream(...)` 若被调用会直接失败，因此 Bean 构造测试不会发起远端请求。

AgentScope 的默认 `JsonFileAgentStateStore` 会在 `HarnessAgent` 构造时创建 `${user.home}/.agentscope/state/<agentId>`。测试在系统属性资源锁保护下，把 `user.home` 临时指向 JUnit 临时目录并在上下文关闭后恢复；这只隔离测试副作用，不改变生产 state store 边界。

`HarnessAgent` 实现 `AutoCloseable`，而 Spring `@Bean` 的默认 `destroyMethod="(inferred)"` 会在应用上下文关闭时调用其公开 `close()`，因此生产 Bean 不需要重复声明销毁方法。配置测试还在断言块的 `finally` 中显式关闭 Bean，确保 AgentScope 持有的 workspace index 与 delegate 在 JUnit 清理临时目录前释放；这属于测试资源生命周期，不改变生产装配。

按当前批次执行纪律，本任务只编写测试，未运行 `mvn compile` 或任何测试；编译、测试与独立验收统一延后到完整批次边界。

## 后续 Issue #8 接口边界

本任务只提供可注入的 `HarnessAgent`。Issue #8 的最简接口负责构造带 `userId` / `sessionId` 的 `RuntimeContext`、调用 agent 并映射 HTTP 请求与响应；不得把 HTTP 或身份逻辑回填到本配置类。本任务也没有提前配置系统 prompt、工具或远端调用验收。

## 非本任务范围

- 不修改 0.3 workspace 或 0.4 model provider 的生产配置；
- 不启用 fallback，不增加第二个 `HarnessAgent` 或新抽象；
- 不选择或替换 AgentStateStore，不配置 trace、memory、compaction、skill 或 subagent；
- 不新增 Controller，也不调用远端模型；
- 不调整迁移期 Spring AI 遗留。
